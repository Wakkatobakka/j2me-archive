J2ME platform history

How Java games got onto phones, and what studios changed to make them run.

Java reaches the keypad

In April 2001, Motorola, Nextel and Sun announced Java applications for the Motorola i85s and i50sx. When Nokia introduced the 3410 in March 2002, it called the phone its first mass-market handset that let independent developers offer Java applications. The color 3510i followed the same year and put downloadable games alongside picture messages and polyphonic ringtones in its sales pitch.[1][2][3]

Getting a game depended on where you lived and what your operator carried. In October 2002, T-Mobile in the Czech Republic extended its Java games service from the Siemens MT50 to three Nokia models. Customers could choose a game through the phone’s WAP browser, on the web, or by SMS.[4]

What the phone downloaded

The Mobile Information Device Profile, or MIDP, gave developers a common set of Java interfaces for phones. Its 2000 specification was followed by MIDP 2.0 in November 2002. A game could be delivered as a MIDlet suite in a JAR containing the program and its resources. A second file, the JAD descriptor, could tell the phone where the JAR lived and let it check the download’s requirements before installing it.[5][6][7]

With MIDP 2.0, a download page could point straight to a JAR. A server could also read the phone model from the browser request and show a menu tailored to that device. That helps explain why an old file collection might contain a JAR alone for one edition and a paired JAR and JAD for another.[7]

What changed from phone to phone

In Game Developer in 2005, Glu showed its Aqua Teen Hunger Force game running at 176×220 and 128×144. The two displays used the same binary. The code added space between the speed and angle meters on the wider screen, and the team built the backgrounds from shared art. On low-memory phones, the same article describes cutting features or drawing animations with fewer frames.[8]

3D gave studios another device capability to work around. The Java Community Process published JSR 184 in December 2003. It specified an optional Java 3D package called M3G. A phone’s MIDP version could tell a developer which basic interfaces were present. Support for M3G still had to be checked separately.[9][10]
